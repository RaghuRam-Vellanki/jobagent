# Session — 2026-05-11

One-shot summary of the work done in this Claude Code session, so a future session can pick up cleanly without re-deriving context.

## Goal of the session

"Land my PM job in 4–6 weeks." User has been getting no callbacks despite the agent applying to dozens of jobs. Strategic gap analysis (from the prior compacted session) identified three root causes:

1. **Keyword-only scoring** pollutes the queue with weak matches.
2. **Frozen resume + static cover letter** can't pass ATS for specific JDs.
3. **Silent skip of custom screening questions** in the Universal Filler produces incomplete applications → auto-reject.

The plan for this session was to attack #3 first (highest leverage, smallest change) plus add a freshness/dedup gate (fast applications get ~5x reply rate; duplicate roles waste daily-cap).

The full V1 product spec was written in plan mode and lives at `C:\Users\pc\.claude\plans\cached-drifting-whale.md`.

## What shipped

### 1. LLM screening-question answerer

New module `backend/llm/`:
- `claude_client.py` — async Anthropic wrapper. Haiku 4.5 for screening, Sonnet 4.6 for cover letters. Profile block cached via `cache_control: ephemeral` (cuts cost ~5x across questions in the same form). Per-user daily cap via `LLM_DAILY_CAP_USD` env var (default $1.50). Gracefully reports `is_enabled() == False` when `ANTHROPIC_API_KEY` is unset → callers no-op.
- `prompts.py` — SCREENING_SYSTEM and COVER_LETTER_SYSTEM templates + user-prompt builders. Screening prompt enforces concise answers, options-as-labels for selects, and `NEEDS_HUMAN` sentinel when profile lacks the data.
- `__init__.py` — re-exports `get_client`, `is_enabled`.
- `requirements.txt` — added `anthropic==0.39.0`.

### 2. Two new DB tables

In `backend/db/models.py`:
- `LLMCall` — one row per Claude API call. Fields: `user_id`, `model`, `purpose` (screening | cover_letter | scoring), `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `cost_usd`, `created_at`. Used for the daily-cap check.
- `ScreeningAnswer` — cache of LLM-generated answers keyed by `(user_id, question_hash)`. Fields: `question_hash` (sha256 of normalized question, first 32 chars), `question_text`, `answer`, `profile_version`, `use_count`. Identical questions across applications cost the LLM only once.

Both tables are created at startup via `Base.metadata.create_all()` (no `_V1_COLUMNS` entries needed since they're brand new).

### 3. Universal Filler — cache-then-LLM fallback

In `backend/agents/universal_filler.py`:
- Replaced the silent skip at the old line 287–289 (synonym-table miss → `fields_skipped.append`) with `_fill_unknown_field(handle, label)`:
  1. Skip if no API key (preserves old behavior).
  2. Determine element type (input / select / radio / textarea / file). File inputs are excluded.
  3. For `<select>`: enumerate option labels and pass to Claude as constrained choices.
  4. Hash the question; look up `ScreeningAnswer` cache.
  5. On miss: call `ClaudeClient.answer_screening_question()`, write to cache.
  6. Fill the field with the answer using the type-appropriate primitive (`_select_option`, `handle.check()`, `handle.fill()`).
  7. On any failure → fall through to old silent-skip behavior.
- Added `fields_llm_answered: int = 0` to `FillResult` and the LinkedIn-external log line.
- Constructor now takes `user_id: int | None = None`; threaded through `linkedin_agent._apply_external`, `ats_aggregator_agent`, both Naukri external paths, and `fill_form()` module helper.
- `_get_profile_dict()` in `api/agent.py` now includes `user_id` so the agents read it from the profile dict (no constructor surgery on every agent class).

### 4. Freshness + dedup gate

Schema (idempotent ALTER TABLE via `_V1_COLUMNS`):
- `Job.posted_at_source: DateTime, nullable, indexed` — when the JD was posted on the source platform.
- `Job.dedup_key: String(32), indexed` — stable per-user role identity.

`backend/api/agent.py`:
- New `_compute_dedup_key(user_id, company, title)` — lowercases both, strips seniority noise (`sr`, `senior`, `jr`, `junior`, `associate`, `lead`, `principal`, `staff`) before hashing. Verified: "Senior PM" / "Sr. PM" / "Lead PM" at Stripe all collide; Adobe PM does not.
- `_save_job()` now returns `bool` (True inserted, False dropped as duplicate). Checks for any prior Job with the same `dedup_key` for this user discovered within the last 30 days.
- `_save_job()` parses `posted_at_source` from either a `datetime` or ISO-string the scraper passes.

`backend/api/jobs.py` (queue endpoint):
- Sort order is now: `posted_at_source DESC NULLS LAST → match_score DESC → discovered_at DESC`. Freshness wins within score band.

### 5. Verified

- DB migration runs cleanly on the existing `data/jobs.db` (`posted_at_source`, `dedup_key` added; `llm_calls`, `screening_answers` tables created).
- `from backend.llm import get_client, is_enabled` imports clean; `is_enabled()` returns False with no key (graceful no-op).
- `FillResult().fields_llm_answered == 0`.
- Dedup key collision/separation verified across Stripe seniority variants and Adobe.

## What's NOT done (deferred for next slice)

These were in the strategic plan but are explicitly not yet shipped:

1. **Scraper-side `posted_at_source` extraction** — LinkedIn agent reads "Posted X hours ago" text but doesn't parse it into a datetime yet. Without this, freshness sort falls back to score → discovered_at. The schema is ready; the parser is the next slice.
2. **Claude-Haiku semantic relevance gate before queueing** — currently the keyword scorer is still the only gate. The plan calls for wrapping `semantic_scorer.score_job()` in `score_job_with_llm()` that runs Claude on borderline jobs. Wire-in point is `api/agent.py:289`.
3. **Cover-letter generator wired into the filler** — `ClaudeClient.write_cover_letter()` exists but isn't called yet from `universal_filler._fill_one("cover_letter_text", …)`. Today the filler uses the static `profile.cover_letter_template`.
4. **Google Forms walker** — has its own `fields_skipped.append` site near line 711 that still silent-skips. Less common path; not blocking.
5. **Funnel logging columns** on Job (`form_fields_total`, `form_fields_filled`, `form_questions_skipped`, `form_questions_llm_answered`, `submit_clicked`, `apply_duration_ms`, `reached_review`) — useful for diagnosing why callbacks aren't coming, but not strictly needed for the LLM filler to work.

## How to activate the LLM filler

```powershell
setx ANTHROPIC_API_KEY sk-ant-...   # one-time, opens new shells with the env var
# restart backend (existing shell won't pick it up)
python backend/serve.py
```

With no key set, the filler reverts to the previous silent-skip behavior. With a key set, daily spend caps at $1.50 by default (`LLM_DAILY_CAP_USD` env var to raise).

Cost model rough numbers (Haiku, screening only):
- ~6 unknown questions per application × 25 apps/day = 150 calls
- Profile block ~600 tokens, cached after first call → ~$0.001/call after cache warm
- Expected steady-state spend: ~$0.15/day for screening. Cover-letter generation (Sonnet) would add ~$0.30/day if turned on.
